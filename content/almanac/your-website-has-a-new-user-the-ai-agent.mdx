For most of my career, I have built websites for humans. Humans can be annoying users, but at least I understand them. They miss buttons, ignore error messages, click the logo to go home, and press Submit three times if nothing happens within half a second.

A few days ago I was listening to [Syntax episode 1037, *WebMCP is here (and you should care)*](https://syntax.fm/show/1037/webmcp-is-here-and-you-should-care), where Wes Bos and Scott Tolinski talked to Sarah Drasner and Dominic Farolino from the Chrome team. I had heard the name WebMCP before, but this was the first time I understood what it might actually change.

One thought stuck with me afterwards: we now have another kind of website user. The AI agent.

It does not care about your typography, your border radius, or the hover animation you spent an afternoon tuning. Given the choice, it might prefer not to use your interface at all. So what does a website look like when some of its users are not human?

![A human reaches product capabilities through the UI, while an AI agent can talk to those capabilities directly.](/almanac/your-website-has-a-new-user-the-ai-agent/human-agent-capabilities.webp)

## The slightly ridiculous way agents use the web today

Imagine telling an agent: "Find me a hotel in Edinburgh next Friday for under £180, with parking, and book it."

The agent can open a hotel site, find the date picker, enter dates, read the results, set filters, choose a room and eventually find the booking button. It is impressive that this works at all. It is also a little ridiculous.

Behind that date picker is probably logic that accepts two dates. Behind Book Now is an action that creates a reservation. The agent does not need either visual element. It needs to know what the site can do, what input each action needs, and whether it has permission to do it.

Right now we often make agents reverse engineer that from the interface.

## WebMCP changes that relationship

This is what made [WebMCP](https://developer.chrome.com/docs/ai/agents) click for me. It is still experimental, so I would not rebuild a production app around it tomorrow. But the idea is simple: a website can explicitly expose structured tools that an AI agent can understand and call.

Instead of guessing which button reserves a room, the agent could see something closer to:

```text
searchHotels()
getRoomAvailability()
reserveRoom()
cancelReservation()
```

The site describes what each tool does and what input it needs. Chrome's current API lets sites register these tools with JavaScript, and there is also work on making normal HTML forms available as tools.

For a human, the route is roughly `Human → UI → Product capabilities`. For an agent, it can become `Agent → Product capabilities`.

The UI still matters. Humans are not going anywhere. But it is no longer necessarily the only doorway into the product.

## Semantic HTML suddenly gets another job

There is a nice irony here. Frontend developers have been told for years to use real buttons, label inputs properly, use headings correctly and stop turning `<div>` elements into buttons.

Accessibility remains the important reason to do this. But agents give semantic HTML another useful property: machines have a better chance of understanding what we built.

![Clear semantic HTML gives software useful meaning. A pile of nested divs gives it much less to work with.](/almanac/your-website-has-a-new-user-the-ai-agent/semantic-html-vs-div-soup.webp)

A button called "Add to basket" carries useful meaning. A clickable `<div>` containing three nested spans, an SVG and seventeen generated CSS classes carries considerably less.

## This changes how I think about frontend architecture

A human shopping for boots might choose waterproof, size 10, under £120, then sort by delivery date. An agent gets: "Find me waterproof walking boots, size 10, under £120, that can arrive by Friday."

Same goal. Different interface.

It makes the separation between **what a product can do** and **how the current UI lets someone do it** more important. We already know business logic should not live inside random React components. Agents just give us another reason to care.

If `addToBasket()` only makes sense when called from `ProductCard.tsx`, exposing it to anything else is going to be unpleasant.

## Then things get scary

Reading hotel prices is harmless. Booking a £1,200 hotel is not.

Once an agent can act, we need to think about permission, intent, confirmation and undo. Did the user ask for this? Does it need approval? Can we reverse it?

[WebMCP's security guidance](https://developer.chrome.com/docs/ai/webmcp/secure-tools) already covers some of this. Tools can flag read only or consequential actions, and the guidance warns about indirect prompt injection, where hostile content tries to influence what an agent does.

![Agents can do more, but consequential actions need clear approval and a reliable way back.](/almanac/your-website-has-a-new-user-the-ai-agent/read-act-confirm-undo.webp)

I suspect undo will become especially important. If software does more on our behalf, I would rather have a clear history and a reliable way to reverse an action than click through twelve "Are you sure?" dialogs.

## I don't think we need to rebuild the web

I do not think every company needs an Agent Experience team by next Tuesday. WebMCP is experimental and will change. Maybe it becomes the standard. Maybe something else wins.

The more interesting change is who might use the things we build. Some users will interact with products through software acting on their behalf rather than through a pair of eyes looking at our interface.

The sensible response is probably boring: use semantic HTML, keep business logic separate from UI code, expose clear product capabilities, and think carefully about which actions can change data.

For years, frontend developers have asked whether a person can understand how to use a website. We might soon need to ask another question too: **can something that has never seen the website understand what it is capable of doing?**

I find that a much more interesting frontend problem than making another button prettier.
